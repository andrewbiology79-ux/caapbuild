============================================================ 1. PROJECT
OBJECTIVE ============================================================

Build a complete, reliable, offline-first Android Question Bank
application.

The application will support:

-   Independent Type_CQ and Chapter_CQ systems.
-   Subject, chapter, topic and question-type hierarchy management.
-   Stimulus-based question groups.
-   Minimum Editor and Full Editor using one shared data model.
-   Question cards and question management.
-   Board and examination-year tagging.
-   Category management.
-   Ordered text/image solutions and mathematical content.
-   Image import, processing, integrity checking and lifecycle
    management.
-   Full-text search, filters and duplicate detection.
-   Question paper creation and immutable source snapshots.
-   Backup and restore.
-   Database migration and crash recovery.
-   Production Android builds and release testing.

The final application must be functional, persistent, recoverable,
testable and suitable for real-world use.

This plan uses the uploaded Room Database Implementation Blueprint as
the architectural baseline. It does not treat the existing ZIP build
harness as a completed application.

Before development proceeds, correct the blueprint's 45-standard-table

============================================================ 3.
ARCHITECTURAL RULES — MUST NOT BE VIOLATED
============================================================

3.1 Application layering

UI -> ViewModel -> UseCase -> Repository -> DAO -> Room / SQLite

-   Activity, Fragment and Compose UI must not access DAOs directly.
-   ViewModels expose observable state and accept UI events.
-   UseCases coordinate domain operations.
-   Repositories enforce business rules and scope boundaries.
-   DAOs contain database operations and explicit SQL queries.

3.2 Scope separation

Type_CQ and Chapter_CQ must have separate:

-   Entity packages where their schemas differ.
-   DAO packages.
-   Repository interfaces and implementations.
-   Domain models where their hierarchy differs.
-   Validation rules.
-   Save and load operations.
-   Tests.

Shared infrastructure should be limited to genuinely shared concepts
such as board catalog, app metadata, media coordination, operation
journal and paper management.

Chapter_CQ must not accidentally access Type_CQ-specific Topic or
QuestionType tables. Type_CQ must not accidentally write Chapter_CQ
data.

3.3 Editor model

Minimum Editor and Full Editor must use the same EditorDraft and save
use case.

Changing editor mode must never: - Clear hidden fields. - Replace
existing values with defaults. - Drop images or relationships. - Remove
solution parts. - Change question identifiers. - Lose unsaved changes.

3.4 Database rules

-   Explicit ORDER BY for all user-visible ordered collections.
-   Flow for observable lists and suspend functions for one-shot
    operations.
-   Use typed projections and explicit JOIN queries where appropriate.
-   Use Room transactions for relational multi-step saves.
-   Never use destructive migration as a production fallback.
-   Export and version-control Room schema JSON.
-   Preserve canonical foreign-key and integrity rules.
-   Define one timestamp unit and use it consistently.
-   Keep file-system operations outside long-running Room transactions.

3.5 Data safety

-   No silent data loss.
-   No silent omission of missing or corrupt images.
-   No deletion of source questions that invalidates paper snapshots.
-   No destructive backup/restore operation while an editor save is
    active.
-   No release until migration, restore and recovery tests pass.

============================================================ 8. RISKS

============================================================

RISK 1: Room schema differs from canonical SQL. Mitigation: Automated

EditorDraft and shared save operation; round-trip tests.

recovery.

migrations, realistic fixtures and backup verification.

Versioned snapshots and independent asset-lifecycle policy.

RISK 8: FTS results become stale. Mitigation: Trigger lifecycle tests
and index rebuild after migration.

RISK 9: Large datasets cause slow cards or search. Mitigation: Query
profiling, indexes, pagination and performance tests.

RISK 10: Feature scope expands without traceability. Mitigation:
Maintain the 146-item audit and formal change log.

============================================================ 14. ARCHITECTURE DECISION UPDATE — VERSION 1.2
============================================================

ADR-001 — ONE PHYSICAL SQLITE DATABASE
Status: ACCEPTED
Decision date: 16 November 2026

The application will use one physical SQLite database file named
`QuestionBank.db`. Do not split Type_CQ, Chapter_CQ, or category data into
separate database files.

Logical separation remains mandatory:
- Type_CQ and Chapter_CQ retain separate table families, DAO boundaries,
  repository boundaries, and use cases.
- Paper-building tables remain in the same database because paper items
  can reference either question source.
- The shared board catalog and operation journal remain in the same
  database as specified by the canonical schema.
- Category tables remain exactly as defined in canonical schema v1.1:
  `type_cq_question_categories`, `chapter_cq_question_categories`, and
  `paper_categories`. This decision selects one physical database; it
  does not merge category semantics or alter the canonical schema.

Consequences:
1. Cross-domain references and paper-source relationships remain within
   one SQLite database boundary.
2. Related relational writes can use one database transaction.
3. Backup, restore, migration, and integrity checks use one database
   boundary.
4. Type_CQ and Chapter_CQ separation is enforced through domain, DAO,
   repository, and UI boundaries rather than separate database files.
5. Any future proposal to merge category tables or redesign category
   ownership requires a separate reviewed architecture decision and a
   migration plan.
