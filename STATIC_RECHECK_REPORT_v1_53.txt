2. DEFECTS FOUND AND CORRECTED
A. Type_CQ duplicate checker used the wrong repository property.
- The editor route called `container.typeCqQuestions.isDuplicate(...)` even though `typeCqQuestions` is a `TypeCqQuestionRepository` and has no `isDuplicate` member.
- `isDuplicate(topicId, questionText)` is declared by `TypeCqRepository`, exposed by `container.typeCqData`.
- Corrected the route to call `container.typeCqData.isDuplicate(topicId, text)`.
- Static interface review indicates the prior call would not compile; the correction has NOT been compiled.

B. Existing archived Type_CQ question type could block unrelated edits.
- `TypeCqQuestionDao.updateGroup` rejected every metadata update whose type was no longer active, even when the question already had that same archived type and the user only changed marks.
- Added `questionTypeOf(questionId)` and changed validation so an archived type may be retained only when it is already the question's stored type. A new or changed assignment to an archived type remains rejected.
- This is a static code correction; no DAO test or Room/KSP validation was run.

C. Full-only solution editing controls were visible in Minimum mode.
- Wrapped the ordered text-solution editor controls (fields, add/remove/reorder actions) in `EditorMode.FULL` for both Type_CQ New and Edit screens.
- The screen hides Full-only controls in Minimum mode; ViewModel draft values are not cleared by this visibility condition. Persistence across mode changes remains unverified.

D. Duplicate warning wording overstated the matching algorithm.
- Type_CQ repository duplicate detection compares exact trimmed question text, not fuzzy/similar wording.
- Adjusted the warning text to say an exactly identical wording was found. This is a wording correction, not a fuzzy duplicate detector.

E. Chapter_CQ could report failure after the write had already committed.
- The DAO transaction now checks the question belongs to the target chapter and performs question/stimulus/solution/board/category read-back checks before returning from the transaction. A failed check throws inside the transaction, causing the enclosing Room transaction to roll back.
- The repository had duplicated those checks after the transaction committed. A late failure there could return `false` even though data was already saved. Removed the post-commit duplicate read-back; the repository now returns the transactional DAO result and catches exceptions as failure.
- Exact Room transaction rollback behaviour is not proven until runtime testing; it was not tested in this iteration.
